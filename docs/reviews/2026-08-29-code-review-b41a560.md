## Remediation status

The follow-up working-tree patch resolves every confirmed bug and code risk:

- reminder edits cancel and re-enqueue the unique periodic work so the selected time establishes a new anchor;
- document-provider read/write failures are caught and reported through the app snackbar;
- movement drafts, history filters, and scalar editor/settings state use saveable state across activity recreation;
- backup decoding/encoding and CSV generation run on an injected background dispatcher;
- new-movement defaults sample the injected clock when the form opens instead of relying on the last Room emission;
- money display/edit conversion is centralized in `MoneyText`, and movement history, Pockets, and Settings were extracted into cohesive screen modules (reducing `PocketApp.kt` from 1,404 lines to under 500);
- CSV cells escape quotes/newlines and neutralize leading spreadsheet formulas;
- rollover subtraction now rejects `Long` overflow;
- a Room 2→3 `MigrationTestHelper` test protects both the known-name icon backfill and preservation of custom names.

The documentation ambiguity and incorrect recovery instruction are also corrected. The application-database shortcut test remains an intentional end-to-end integration test with pre-test and `finally` cleanup. The host/device ledger overlap is retained intentionally for platform parity; it is a maintenance tradeoff rather than a correctness defect. Verification results are recorded at the end of this report.

## 1. Confirmed code bugs

### B1. Editing an active reminder does not reliably move it to the newly selected time — `Reminder.kt:37-43`

```kotlin
val request = PeriodicWorkRequestBuilder<ReminderWorker>(24, TimeUnit.HOURS)
    .setInitialDelay(Duration.between(now, next))
    .build()
manager.enqueueUniquePeriodicWork(WORK_NAME, ExistingPeriodicWorkPolicy.UPDATE, request)
```

The project uses WorkManager 2.11.2. Its `UPDATE` policy preserves the existing work's original enqueue time and period count. Once the periodic worker has run, its next execution remains anchored to the existing 24-hour period; the new initial delay does not re-anchor the schedule to the time at which the user saved the change. Initial scheduling and re-enabling after cancellation still work, so the defect is specifically editing an already-active schedule—not that reminder time “never applies.”

If changing the selected time must establish a new anchor, use `CANCEL_AND_REENQUEUE` (the explicit current equivalent of deprecated `REPLACE`) or a scheduling design based on one-time work/next-schedule overrides. WorkManager remains best-effort, as required by the product spec.

### B2. Backup import/export IO failures can crash or fail silently — `MainActivity.kt:29-46, 75-82`

The restore reader and export writer run on `Dispatchers.IO`, but their surrounding `lifecycleScope.launch` blocks do not catch `IOException`, `SecurityException`, or other provider failures. Exceptions escape the launched coroutine; a revoked/deleted document or storage/provider failure can terminate the process. A provider returning a null stream also results in no import/export with no user feedback.

This threatens operation completion and user trust, not ledger transactionality: restore replacement itself remains transactional once valid bytes reach the ledger.

### B3. User-entered form and filter state is lost on activity recreation — `ProductionExpense.kt:82-113`, `PocketApp.kt:464-469`

The movement form stores amount, Pocket, type, merchant, note, payment method, currency, conversion state, date, and time with `remember(stateKey)`. Only `detailsExpanded` uses `rememberSaveable`. Rotation recreates the activity and resets the entered values even though the serializable Navigation 3 route is retained by `rememberNavBackStack` (`PocketApp.kt:209`). The same pattern affects movement search/filter/selection state and several editor/settings fields (`PocketApp.kt:940-943, 1015-1017, 1155-1167`).

## 2. Confirmed code risks

- **R1. Backup preview performs JSON decoding and validation on the main dispatcher** — `PocketApp.kt:154-157` calls `ledger.previewBackup` from `LaunchedEffect`; `RoomPocketLedger.kt:324` delegates directly; `BackupCodec.kt:35-40, 98-147` synchronously converts, decodes, and validates as much as 10 MiB. Main-thread jank is supported by inspection. ANR is possible but has not been benchmarked, so it is not stated as an observed failure.
- **R2. Default movement date/time can become stale across midnight** — `RoomPocketLedger.kt:22-43, 260, 316-321` samples the clock only while rebuilding `LedgerState` from Room emissions. Merely navigating to the movement form does not cause an emission. `ProductionExpense.kt:97-109` therefore can initialize a post-midnight movement with the previous day's cached date/time in a long-running session.

The earlier `ACTION_NEW_EXPENSE`/`onNewIntent` finding was removed. `MainActivity` uses the default launch mode (`AndroidManifest.xml:13-16`), and the current static-shortcut path recreates the activity and reaches `onCreate`; there is no demonstrated production `singleTop` path that requires `onNewIntent` handling.

## 3. Design smells (judgement calls)

- **Large, mixed-responsibility UI file:** `PocketApp.kt` is 1,404 lines and contains root navigation, onboarding, screens, settings sections, and multiple dialogs. This increases maintenance cost, although it is not evidence by itself that it caused B3.
- **Fragmented money formatting:** `PocketApp.kt:1395, 1402-1404` and `ProductionDashboard.kt:356-359` duplicate the grouped SAR display pipeline. `ProductionExpense.kt:440-441` performs the related minor-to-major conversion for editable input using `toPlainString`, not the same `DecimalFormat` pipeline. `Money.toMajorString()` also lacks grouping and the `SAR` prefix, so it is not a drop-in replacement. A shared formatter should distinguish display formatting from editable form formatting.

## 4. Tests and build

The existing tests meaningfully cover money parsing/summary/projection boundaries; JSON backup round trips; truncated, incompatible, and relationally invalid backups; restoration into a separate non-empty database; rollback behavior; and period behavior. The manifest backup rules exclude the database, and the build declares minSdk 26, targetSdk 36, release minification, guarded environment-based signing, and Room schema export.

Confirmed gaps and maintenance risks:

- **No Room migration test:** schemas 1–3 are exported and `MIGRATION_2_3` is handwritten (`FinanceDatabase.kt:169-188`), but neither host nor device tests use `MigrationTestHelper` or otherwise exercise an on-disk 2→3 migration.
- **CSV coverage is shallow, not absent:** host assertions at `PocketLedgerHostBehaviorTest.kt:115-118` and device assertions at `PocketLedgerBehaviorTest.kt:141-144` verify the header, merchant, and amount. They do not verify all columns, ordering, quoting/escaping, embedded newlines, or spreadsheet-formula neutralization.
- **The shortcut device test mutates the application database:** `PocketAppFlowTest.kt:227-250` clears and initializes the real `PocketApplication.database`, then clears it in `finally`. Pre/post cleanup limits ordinary sequential-test risk, but shared or parallel execution could still interfere.
- **Host/device ledger suites are near-mirrors:** the duplication provides platform parity but can drift; the host suite already includes legacy-v1/icon coverage that the device suite lacks.

No release build or runtime minification check was performed by this review, so “build configuration is sound” is not asserted beyond the configuration facts above.

## 5. Documentation and specification

### D1. ADR 0001 does not distinguish accepted target behavior from current behavior

`docs/adr/0001-plaintext-portable-backup-and-replacement-restore.md:8-12` uses present-tense language for several accepted decisions that are not implemented at `b41a560`:

- `BackupCodec.kt:13-33, 159-167` serializes Room entities but not DataStore reminder settings.
- Restore does not disable a previously enabled reminder.
- The restore dialog (`PocketApp.kt:161-197`) does not offer a pre-replacement safety export.
- The export flow does not provide the stated persistent plaintext explanation or first-use confirmation.

The gaps are real, but an accepted ADR may record intended behavior before delivery. The defect is status ambiguity, not necessarily that the decision itself is wrong. `docs/product/FUTURE_UPDATES_DECISION_SPEC.md:28-39, 124-134` correctly describes these items as future work.

### D2. The recovery guide incorrectly says non-empty restores are rejected

`Info/release-signing-and-recovery.md:79` says restore intentionally rejects non-empty targets. The implementation instead transactionally clears and replaces all ledger tables (`BackupCodec.kt:42-68`), and both host and device ledger tests successfully restore into an initialized target. This safety-relevant recovery instruction should be updated.

The earlier “stale schema version” finding was removed. `docs/product/FUTURE_UPDATES_DECISION_SPEC.md:9, 17-26` explicitly describes commit `61f5782`, where Room schema version 2 was correct; it does not claim that version 2 is the current schema at `b41a560`.

## 6. Confirmed strengths and limits

- `PocketMath.summary` uses exact addition/subtraction and `PocketMath.project` uses bounded `BigInteger` arithmetic (`DomainRules.kt:80-121`). This does not justify the broader previous claim that every money path is overflow-guarded; `PocketMath.rollover` still uses ordinary subtraction at line 111.
- Backup validation is extensive, replacement occurs within one Room transaction, and the input reader deliberately reads one byte beyond the 10 MiB limit so the codec can reject oversized data.
- Migration 2→3 is a fixed-point icon backfill by inspection: it only updates rows still stored as `OTHER`. Its behavior is not protected by an automated migration test.
- Edge-to-edge setup, DataStore-backed preferences, immutable explicit notification intent, private notification visibility, fixed test clocks, and polling-based Compose synchronization are present in source.
